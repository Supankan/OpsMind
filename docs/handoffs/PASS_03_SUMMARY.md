## 1. Executive Summary

Pass 03 establishes a reproducible, live **System-Under-Test (SUT)** based on the OpenTelemetry Demo (Astronomy Shop) release `3.0.0` running in minimal core + official observability stack mode.

This pass proves that:
1. Pinned OpenTelemetry Demo `3.0.0` runs reliably on the local workstation within existing WSL2/Docker resource bounds (~2.8 GB total SUT memory footprint).
2. Synthetic shopping traffic is continuously generated by k6 (`load-generator`).

4. The `paymentServiceUnreachable` fault (via flagd feature flag `paymentUnreachable`) can be injected and cleanly reset.

   - **Traces:** GRPc `Unavailable` (code 14) and `name resolver error: produced zero addresses` on `oteldemo.PaymentService/Charge`, propagated to HTTP 500 on `frontend` and `frontend-proxy`.

   - **Metrics:** `traces_span_metrics_calls_total{service_name="checkout", span_name="oteldemo.PaymentService/Charge", status_code="STATUS_CODE_ERROR"}` incremented during the fault window.
6. The environment cleanly recovers to a zero-error baseline upon fault reset.
7. An evaluator-only baseline manifest has been established with strict ground-truth isolation from future RAG vector stores.
8. The existing OpsMind control plane remains 100% green (52/52 tests pass, zero lint/format/type/migration regressions).

## 8. Prometheus Telemetry Findings

- **Ingestion Mechanism:** Push-based OTLP receiver (`--web.enable-otlp-receiver`) receiving metrics from `otel-collector` at `http://prometheus:9090/api/v1/otlp`.
- **Key Useful Metric Names Identified:**
  - `traces_span_metrics_calls_total`: Highly responsive span metric generated by the OTel collector's `spanmetrics` connector. Segments by `service_name`, `span_name`, `span_kind`, and `status_code` (`STATUS_CODE_OK` vs `STATUS_CODE_ERROR`).
  - `rpc_client_call_duration_seconds_count`: gRPC client RPC counters segmented by `service_name`, `rpc_method`, and `rpc_response_status_code`.
  - `http_server_duration_milliseconds_count`: HTTP request counters for frontend and web proxy.
  - `k6_http_reqs_total`: Synthetic traffic generation volume.

## 9. OpenSearch Log Findings

- **Index Format:** Daily date-stamped indices formatted as `otel-logs-YYYY-MM-DD` (active index during verification: `otel-logs-2026-09-03`).
- **Cluster Status:** `status: yellow` (1 primary shard, single-node cluster with replica unassigned, standard for local single-node dev).
- **Key Schema Fields:**
  - `@timestamp`: Log event generation timestamp (ISO8601 UTC).
  - `resource.service.name`: Emitting service identifier (e.g. `"checkout"`, `"frontend-proxy"`, `"product-catalog"`).
  - `severity.text`: Normalized log severity level (`"INFO"`, `"WARN"`, `"ERROR"`).
  - `body`: Raw log message text or access log string.
  - `attributes.*`: Structured contextual key-values.

## 16. Known Limitations

- **Checkout Service Internal Logging:** While `checkout` emits distributed spans with full error attributes and exception events to Jaeger, its direct log statements (`slog`) only fire on success (`"payment went through"`), meaning log evidence for payment failure is found in `frontend-proxy` access logs rather than checkout stdout.
- **Jaeger Base Path Routing:** As designed upstream, Jaeger query API routes must be prefixed with `/jaeger/ui/api/*`.
- **OpenSearch Cold Start:** Requires up to 70 seconds on initial cold start to initialize internal plugins.
